# سفارش‌یار

سفارش زنده سر میز و نمایش آن در آشپزخانه برای کافه‌رستوران‌ها.
محدودهٔ پروژه در [SCOPE.md](./SCOPE.md) و تصمیم‌های فنی در [DECISIONS.md](./DECISIONS.md) آمده‌اند.

> وضعیت: در حال ساخت. فاز ۰ و ۱ (اسکلت و دیتابیس) انجام شده است. احراز هویت، سفارش و آشپزخانه هنوز ساخته نشده‌اند.

## پیش‌نیازها

- Node.js 20.6 یا بالاتر
- PostgreSQL 16، به یکی از دو روش:
  - **Docker** (با `npm run db:up`)
  - **نصب مستقیم:** PostgreSQL را نصب کنید و دیتابیس بسازید:
    `CREATE DATABASE sarfaresh;`

## راه‌اندازی محلی

```bash
cp .env.example .env.local      # در ویندوز: copy .env.example .env.local
npm install
npm run db:up                   # فقط اگر از Docker استفاده می‌کنید
npm run db:migrate              # ساخت نقش برنامه، جدول‌ها و سیاست‌های RLS
npm run dev                     # http://localhost:3000
```

در `.env.local` مقدار `SESSION_SECRET` را با یک رشتهٔ تصادفی حداقل ۳۲ نویسه‌ای عوض کنید و اگر PostgreSQL را مستقیم نصب کرده‌اید، رمز واقعی کاربر `postgres` را در `DATABASE_URL_ADMIN` بگذارید.

بررسی سلامت: `http://localhost:3000/api/health` باید `{"status":"ok"}` برگرداند.

## معماری (تا اینجا)

- **Next.js (App Router) + TypeScript**: رابط راست‌به‌چپ و API در یک پروژه.
- **PostgreSQL 16**: همهٔ دادهٔ هر رستوران با `restaurant_id` علامت‌گذاری شده است.
- **جداسازی رستوران‌ها در دو لایه:**
  1. Row Level Security: برنامه با نقش محدود `sarfaresh_app` وصل می‌شود که Superuser نیست و RLS را دور نمی‌زند.
  2. کلید خارجی ترکیبی `(id, restaurant_id)`: هیچ رکوردی نمی‌تواند به رکورد رستوران دیگر اشاره کند.
- **`withTenant`** (در `src/server/db.ts`): همهٔ پرس‌وجوها درون تراکنشی اجرا می‌شوند که رستوران فعلی را با `set_config` تنظیم می‌کند. اگر تنظیم نشود، هیچ ردیفی دیده نمی‌شود.
- **آیتم‌های سفارش ردیف جدا هستند**، نه JSON داخل سفارش، تا افزودن هم‌زمان باعث گم شدن تغییر نشود.
- **اعتبارسنجی env** هنگام شروع با Zod. تنظیمات ناقص باعث توقف برنامه می‌شود.
- **لاگ ساخت‌یافته** با Pino و حذف فیلدهای حساس.
- **احراز هویت:** کوکی HttpOnly امضاشده؛ نقش و فعال بودن عضویت در هر درخواست از دیتابیس خوانده می‌شود. ساخت کاربر: `npm run user:create -- --help` (ببینید پارامترها در `scripts/create-user.mjs`).
- **تست دودی ورود:** `npm run smoke:auth` (سرور باید در حال اجرا باشد).
- **هسته سفارش** (`src/server/orders.ts`): باز کردن سفارش، افزودن آیتم، لغو و بستن میز، همه idempotent. جزئیات هم‌زمانی در DECISIONS.md (D20 تا D26).
- **تست دودی سفارش:** `npm run seed:min` و بعد `npm run smoke:orders` (سرور باید در حال اجرا باشد). این تست افزودن هم‌زمان، درخواست تکراری، تلاش بین‌رستورانی و مجوزها را بررسی می‌کند.
- **آشپزخانه و به‌روزرسانی زنده:** `GET /api/kitchen/queue`، `POST /api/order-items/:id/status` (با `from` و `to`) و جریان SSE در `GET /api/events/stream`. جزئیات در DECISIONS.md (D27 تا D32).
- **تست دودی آشپزخانه:** `npm run smoke:kitchen`.
- **رابط:** صفحه‌های `/login`، `/tables`، `/orders/:id` و `/kitchen`. هر صفحه با یک هوک (`src/lib/use-live.ts`) از طریق SSE تازه می‌شود، با بازخوانی هنگام اتصال، هر ۳۰ ثانیه و هنگام برگشت تب.

## ساختار پوشه‌ها

```
src/app/        صفحه‌ها و API
src/lib/        ابزارهای مشترک (env, logger)
src/server/     کد فقط سمت سرور (دیتابیس، ...)
db/migrations/  فایل‌های SQL شماره‌دار
scripts/        اسکریپت اجرای Migration
```

## متغیرهای محیطی

| نام | کاربرد |
|---|---|
| `DATABASE_URL` | اتصال برنامه (نقش محدود) |
| `DATABASE_URL_ADMIN` | فقط برای Migration و Seed، هرگز در برنامهٔ در حال اجرا استفاده نمی‌شود |
| `APP_DB_PASSWORD` | رمز نقش برنامه هنگام ساخت آن |
| `SESSION_SECRET` | کلید امضای نشست (حداقل ۳۲ نویسه) |
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error` |

## بررسی دستی جداسازی رستوران‌ها

در `psql` با کاربر مدیر، دو رستوران بسازید، سپس با نقش برنامه:

```sql
SET ROLE sarfaresh_app;
SELECT count(*) FROM restaurants;                    -- 0: بدون رستوران تنظیم‌شده چیزی دیده نمی‌شود
BEGIN;
SELECT set_config('app.restaurant_id', '<id-a>', true);
SELECT slug FROM restaurants;                        -- فقط a
INSERT INTO dining_tables (restaurant_id, label) VALUES ('<id-b>', '1');  -- خطای RLS
ROLLBACK;
```

این بررسی در فاز ۷ به تست خودکار تبدیل می‌شود.

## آزمون‌ها

```bash
npm test
```
قبل از اجرا `npm run dev` را خاموش کنید. تست‌ها یک دیتابیس تازه به نام `sarfaresh_test` می‌سازند، Migration واقعی را اجرا می‌کنند و سرور را روی پورت ۳۱۰۰ بالا می‌آورند. به دیتابیس توسعه و دادهٔ دمو دست نمی‌زنند.

| فایل | چه چیزی را ثابت می‌کند |
|---|---|
| `db-isolation` | RLS و کلیدهای خارجی ترکیبی با نقش محدود دیتابیس، حتی بدون کد برنامه |
| `api-workflow` | یک سرویس کامل میز از باز شدن تا بسته شدن، همراه با جریان زنده |
| `api-security` | نقش‌ها، رستوران دیگر، توکن جعلی، ورودی بد، Origin، قفل ورود |
| `api-concurrency` | درخواست تکراری، افزودن‌های هم‌زمان، رقابت لغو و شروع، رقابت بستن و افزودن، کامل بودن فید رویداد |
| `api-stream` | بازیابی بعد از قطع، جداسازی رستوران‌ها، بسته شدن جریان پس از لغو دسترسی |

آنچه تست نمی‌شود و دلیلش در `DECISIONS.md` (D45) آمده است.

## قابلیت هوش مصنوعی: ورود منو از متن

مدیر متن منو را می‌چسباند، پیش‌نویس را می‌بیند و ویرایش می‌کند، و بعد تأیید می‌کند. **چیزی بدون تأیید مدیر ذخیره نمی‌شود.**

- **قواعد ساده اول:** متن مرتب (`نام - قیمت`) بدون AI خوانده می‌شود. AI فقط برای متن نامرتب (مثلاً قیمت به حروف) یا با دکمهٔ «تحلیل با هوش مصنوعی» صدا زده می‌شود.
- **خرابی بی‌ضرر:** اگر AI جواب ندهد، پاسخ نامعتبر بدهد یا سقف مصرف تمام شود، نتیجهٔ قواعد ساده نشان داده می‌شود. ثبت سفارش هیچ‌وقت به AI وابسته نیست.
- **داده‌ای که می‌رود:** فقط متن منو. نه سفارش، نه مشتری، نه نام کارکنان.
- **امنیت:** متن منو داده‌ٔ غیرقابل‌اعتماد است. دفاع‌ها: DECISIONS.md (D49).
- **هزینه:** ۱۰ درخواست در ساعت و ۳۰ در روز برای هر رستوران؛ توکن و تأخیر هر درخواست در جدول `ai_requests`.

| متغیر | کاربرد |
|---|---|
| `AI_PROVIDER` | `anthropic`، `openai` (هر سرویس سازگار) یا خالی برای خاموش. `mock` فقط برای تست. |
| `AI_API_KEY`, `AI_MODEL` | الزامی وقتی ارائه‌دهنده انتخاب شده. نام مدل را از مستندات سرویس بردارید. |
| `AI_BASE_URL` | اختیاری، برای سرویس‌های سازگار یا آدرس جایگزین |
| `AI_TIMEOUT_MS` | پیش‌فرض ۲۰۰۰۰ |

آزمودن با سرویس واقعی: `npm run smoke:ai` (فقط روی سرور؛ از ایران ممکن است در دسترس نباشد).

**نمونهٔ متن نامرتب برای دمو:** فایل `scripts/smoke-ai.mjs`.
